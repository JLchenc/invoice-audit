## 步骤

1. **arq worker**：`workers/worker.py` 定义 `process_document_job(ctx, document_id)`——从 DB 读文件路径，调 P4 的 `process_document`，回写状态（matched/review/exception）。失败处理：`retry_count += 1`，`raise Retry(defer=…)` 交给 arq 重投；3 次仍失败 → `status='failed'`（不阻塞队列）
2. **入口统一**（双入口，一队列，同一条链路）：
   - 上传 API：写 `invoice_documents(status=pending, source=upload)` → `arq.enqueue_job("process_document_job", id)`
   - cron：`WorkerSettings.cron_jobs` 里 `cron(run_scheduled_batch, hour=23, minute=0, unique=True)`，扫 `source='scheduled'` 且 `pending` 的入队
   - **演示用**：`POST /api/documents/run-batch` 手动触发一次批量（不用等 23:00）
3. **为什么这么拆**（对着前端理解）：API 进程只做「收件 + 开回执」（毫秒级），真正 3~20 秒的 LLM 链路在 worker 进程。上传接口立刻返回 `pending`，前端轮询 `GET /api/documents` 看状态变化——这就是扫描件池页 9 步 stepper 的数据来源
4. **验收**：上传一张票 → worker 日志看到 L1→L5 → DB 状态从 pending 变 matched/review/exception → trace 表 ≥5 条记录且 trace_id 相同

### 核心概念：队列、worker、cron（前端视角）

| 后端概念 | 前端类比 |
| --- | --- |
| **arq worker 进程** | 常驻的 **Service Worker / Web Worker**：独立于页面（API 进程）活着，专职干重活 |
| **Redis 队列** | `postMessage` 消息通道：主线程丢任务（`enqueue_job`，参数会被 JSON 序列化），worker 收到执行 |
| **为什么 API 不自己跑链路** | 相当于不在事件循环里跑 10 秒的同步计算——uvicorn 的事件循环被 LLM 调用卡住，所有请求都会超时 |
| **cron 23:00** | `setInterval` 定时器，但**任务状态持久化在 Redis**：进程重启、错过时间点都能补跑，不像内存定时器一刷新就没了 |
| **Retry 重投** | 失败的任务隔几秒自动重新入队，计数达到上限标记失败——类比请求拦截器的 retry，但带持久化 |
| **双入口一队列** | 两个按钮（手动上传 / 夜间定时）dispatch 同一个 action，reducer（链路）只有一份——行为必然一致 |

> 已实测确认：arq 源码对 Windows 做了兼容（`worker.py:798` 捕获了 win32 不支持 `add_signal_handler` 的异常），直接 `uv run arq ...` 即可，**不需要**切 `WindowsSelectorEventLoopPolicy`。

## 常见坑（正文版，附录有展开）

- worker 和 API 是**两个进程、两个终端**，都要起；改了代码两边都要重启（arq 没有 --reload）
- `enqueue_job` 的参数必须是 JSON 可序列化的（int/str/dict/list）——传 ORM 对象会炸，传 `document_id` 这种主键就行
- 演示期 `max_jobs=1`：重复票判定依赖处理顺序（0046 必须晚于 0003 处理），并发会把两张重复票同时判成 pass

### Python 新人须知（P5 专用）

- **`ctx` 是什么**：arq 给每个任务函数注入的第一个参数（我们不用它就拿 `_`），里面有 `ctx["redis"]`（入队用的连接池）。类比 React 的 `context`——框架塞给你的环境对象。
- **`raise Retry(defer=10)`**：arq 的重试语义——抛这个异常，任务延迟 10 秒重新入队，**不是 Python 普通异常**。类比：Promise reject + 拦截器安排重试。
- **`UploadFile`**：FastAPI 的文件上传句柄。`await file.read()` 拿到完整字节（20MB 内可接受）；`file.filename` 是原始文件名（用户上传时的名字，只用于展示）。
- **`%PDF` 魔数**：PDF 文件头固定是 `%PDF-`。校验文件类型别信 `content_type`（前端可伪造），信文件内容本身。
- **`status_code=201`**：REST 惯例——创建资源返回 201 Created 而不是 200。

### 1) `server/app/workers/worker.py`

```python
"""arq worker：消费 Redis 队列跑 Agent 链路 + 每天 23:00 定时批量。

启动（server/ 目录下，另开一个终端）：
    uv run arq app.workers.worker.WorkerSettings

与 uvicorn 的关系：两个独立进程。API 只入队（毫秒级），本进程跑链路（秒级）。
"""
from __future__ import annotations

from arq import Retry, cron
from arq.connections import RedisSettings
from sqlalchemy import select

from app.core.config import get_settings
from app.db.base import SessionLocal
from app.models.app_models import InvoiceDocument
from app.pipeline.runner import process_document

MAX_RETRIES = 3


async def process_document_job(ctx, document_id: int) -> str:
    """队列任务：一个 document_id 一条 job。

    - 幂等：runner 内部检查 status，处理过的直接返回（arq 重复投递不炸）
    - 失败：计次 + Retry 重投；3 次后 status='failed'（异常池），trace 里已有 error 行
    """
    async with SessionLocal() as session:            # 每条 job 独立会话（worker 没有 FastAPI 帮你管）
        doc = await session.get(InvoiceDocument, document_id)
        if doc is None:
            return "missing"                         # 文档已被删：安静跳过，别让整个队列卡住
        try:
            return await process_document(session, document_id)
        except Exception:
            doc.retry_count = (doc.retry_count or 0) + 1
            if doc.retry_count >= MAX_RETRIES:
                doc.status = "failed"
                await session.commit()
                return "failed"
            await session.commit()
            raise Retry(defer=10 * doc.retry_count)  # 10s → 20s → 30s 递增退避


async def run_scheduled_batch(ctx) -> int:
    """cron 23:00：扫 source='scheduled' 且 pending 的单据批量入队。

    「夜间批量」的真实形态：扫描仪池白天堆积，深夜无人值守统一处理。
    与上传共用同一个 job 函数——同一条链路、同一套 trace，行为必然一致。
    """
    async with SessionLocal() as session:
        ids = (await session.execute(
            select(InvoiceDocument.id).where(
                InvoiceDocument.source == "scheduled",
                InvoiceDocument.status == "pending"))
        ).scalars().all()
    for doc_id in ids:
        await ctx["redis"].enqueue_job("process_document_job", doc_id)
    return len(ids)


class WorkerSettings:
    """arq 的配置对象（类比 vitest 的 defineConfig / vite 的 config），
    `uv run arq app.workers.worker.WorkerSettings` 会读取它起进程。"""
    functions = [process_document_job]
    cron_jobs = [cron(run_scheduled_batch, hour=23, minute=0, unique=True)]
    redis_settings = RedisSettings.from_dsn(get_settings().redis_url)
    max_jobs = 1          # ⚠️ 演示期=1：判重依赖处理顺序（常见坑❷）。生产开并发前先解决判重竞态
    job_timeout = 300     # LLM 是慢 I/O：单 job 给足 5 分钟
    max_tries = 5         # arq 自身重投上限（我们的 Retry 逻辑之上的兜底）
```

### 2) `main.py` lifespan 增补（arq 连接池）

```python
# main.py 的 import 区加：
from arq import create_pool
from arq.connections import RedisSettings

# lifespan 里加两行（Redis 探活那段的旁边）：
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.redis = aioredis.from_url(settings.redis_url, decode_responses=True)
    app.state.arq = await create_pool(RedisSettings.from_dsn(settings.redis_url))   # ← 新增
    yield
    await app.state.arq.close()                     # ← 新增
    await app.state.redis.aclose()
    await engine.dispose()
```

> 一个 Redis 起两个客户端不冲突：`aioredis` 用来探活/缓存，`arq` 的池用 arq 自己的序列化协议投递任务。类比：同一个后端，fetch 实例和 WebSocket 客户端各一个。

### 3) `server/app/api/biz.py`（最小版上传 + 手动批量）

```python
"""业务面路由。P5 只做「能入队」的最小版；P6 补齐鉴权、列表/详情、响应模型。"""
from __future__ import annotations

import uuid
from pathlib import Path

from fastapi import APIRouter, Depends, File, HTTPException, Request, UploadFile
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.db.base import get_session
from app.models.app_models import InvoiceDocument

router = APIRouter(prefix="/api", tags=["biz"])

# biz.py 在 server/app/api/ → parents[3] 是项目根（data/ 的父目录）
ROOT = Path(__file__).resolve().parents[3]
INVOICE_DIR = ROOT / "data" / "invoices"
UPLOAD_DIR = INVOICE_DIR / "uploads"   # ← 故意放 invoices 下面：前端 invoiceUrl 拼的就是
                                       #    /data/invoices/<相对名>，上传票零前端改动即可预览
MAX_SIZE = 20 * 1024 * 1024            # 20MB（和前端上传 Modal 同规则，前后端双重校验）


@router.post("/documents", status_code=201)
async def upload_document(request: Request, file: UploadFile = File(...),
                          session: AsyncSession = Depends(get_session)) -> dict:
    """上传扫描件：存文件 → 建 pending 行 → 入队。毫秒级返回，处理异步进行。"""
    raw = await file.read()
    if len(raw) > MAX_SIZE:
        raise HTTPException(413, "文件超过 20MB 上限")
    if not raw.startswith(b"%PDF"):
        raise HTTPException(400, "只接受 PDF 文件")     # 校验魔数，不信 content_type

    UPLOAD_DIR.mkdir(parents=True, exist_ok=True)
    rel = f"uploads/{uuid.uuid4().hex}.pdf"             # 前端 pdfFile 契约：相对 data/invoices 的路径
    (INVOICE_DIR / rel).write_bytes(raw)

    doc = InvoiceDocument(
        file_name=file.filename or rel,                 # 展示用原始文件名
        file_path=str((INVOICE_DIR / rel).resolve()),   # 处理用绝对路径
        source="upload", status="pending",
    )
    session.add(doc)
    await session.flush()                               # 先拿 id，再入队
    await request.app.state.arq.enqueue_job("process_document_job", doc.id)
    await session.commit()
    return {"id": doc.id, "file_name": doc.file_name, "status": "pending"}


@router.post("/documents/run-batch")
async def run_batch(request: Request,
                    session: AsyncSession = Depends(get_session)) -> dict:
    """演示用：手动触发一次夜间批量（不用等 23:00）。"""
    ids = (await session.execute(
        select(InvoiceDocument.id).where(
            InvoiceDocument.source == "scheduled",
            InvoiceDocument.status == "pending"))
    ).scalars().all()
    for doc_id in ids:
        await request.app.state.arq.enqueue_job("process_document_job", doc_id)
    return {"enqueued": len(ids)}
```

### 4) `server/scripts/seed_documents.py`（模拟夜间到达的 50 张）

```python
"""把 data/manifest.json 的 50 张票注册进扫描件池（source='scheduled'，status='pending'）。
幂等：按 file_name 跳过已注册的。跑完配合 run-batch 即可演示「夜间批量」。"""
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

import asyncio
import json

from sqlalchemy import select

from app.db.base import SessionLocal
from app.models.app_models import InvoiceDocument

DATA = Path(__file__).resolve().parent.parent.parent / "data"


async def main():
    manifest = json.loads((DATA / "manifest.json").read_text(encoding="utf-8"))
    async with SessionLocal() as session:
        existing = set((await session.execute(
            select(InvoiceDocument.file_name))).scalars())
        added = 0
        for inv in manifest["invoices"]:
            name = Path(inv["file"]).name
            if name in existing:
                continue
            session.add(InvoiceDocument(
                file_name=name,
                file_path=str((DATA / inv["file"]).resolve()),
                source="scheduled", status="pending",
            ))
            added += 1
        await session.commit()
        print(f"新增 {added} 张（已存在 {len(existing)} 张跳过）")


if __name__ == "__main__":
    asyncio.run(main())
```

### P5 常见坑（踩之前先读）

- **❶ 两个终端缺一不可**：`uvicorn` 起的是 API 进程（只入队），`arq` 起的是 worker 进程（真处理）。只起 API：上传返回 pending 但永远不变——**任务躺在 Redis 队列里没人消费**，`redis-cli -p 6380 llen arq:queue` 能看到堆积。arq 没有 `--reload`，改 worker 代码要手动重启。
- **❷ 重复票判定 vs 并发**：判重（P3/P4 的 `seen`）依赖「原票先处理完」。`max_jobs=1` 串行保证顺序；一旦开并发，0046 可能在 0003 之前处理，两张都判 pass。生产解法是数据库唯一约束 + `ON CONFLICT` 原子判重（`invoice_fields` 上建 `(field_name, field_value)` 部分唯一索引），演示期用串行最省事——**这是有意识的取舍，面试可以讲**。
- **❸ `enqueue_job` 第一个参数是函数名字符串**：`enqueue_job("process_document_job", doc.id)`——跨进程传不了函数对象，传注册名 + JSON 参数。写错函数名不会立刻报错，worker 端报 `function not found`，注意看 worker 日志。
- **文件路径跨进程**：API 写入的 `file_path` 是绝对路径（`.resolve()` 后的），worker 在同一台机器读没问题；容器化部署时两边要挂同一个卷（v1.0 本地存储的边界，PRD 已声明）。
- **`413 Request Entity Too Large`**：uvicorn 对请求体没默认限制，但走 Nginx/网关时默认 1MB 会拦——部署时记得调 `client_max_body_size`。
- **cron 时区**：arq 的 cron 用 **UTC**。23:00 北京时间 = `hour=15, minute=0` UTC。演示用 `run-batch` 手动触发不受影响；真要对齐「北京时间 23:00」，写成 `cron(run_scheduled_batch, hour=15, minute=0, unique=True)` 并注释清楚。
- **worker 里别用 `get_session` 依赖**：那是 FastAPI 的注入函数（yield 生成器）。worker 里直接 `async with SessionLocal() as session:`，自己管生命周期。
